explain each blocking finding in the diff summary

When a diff has at least one blocking change (regressed, less_reliable, unassessed, less_covered or removed), render_markdown now adds a '#### Why the gate failed' section right after the existing changes table. This Markdown goes to summary.md and to the --markdown destination, such as $GITHUB_STEP_SUMMARY or a PR comment body. The section first states the threshold that was applied, using the existing value formatting, so 1.0 prints as 1: 'Numeric scores pass at threshold 1; categorical verdicts use the source tool's pass mark.' A table follows with one row per blocking finding, in the existing sort order and capped by the existing row limit. Each row gives the kind, with ' (within noise)' when the row is within sampling noise, then a combined Case / check cell, the Baseline and Current fractions, and the Failing attempt. For regressed, less_reliable and unassessed rows, the Failing attempt is the first current attempt that did not pass, shown with its value and evidence and leaving out any part that is absent. Removed checks show 'not recorded in the current run' plus their baseline attempt. Less_covered checks show both assessed counts. Missing or malformed detail reads 'no attempt detail recorded'. Untrusted text is escaped into a single cell and cut to 120 characters with an ellipsis. When there are more rows than the limit, a line gives the remaining count and points to diff.json. A provenance line with each input's file name and the first 12 hex characters of its sha256 appears only when both runs record them. Summaries with no blocking change are unchanged, and so are diff.json, index.html, exit codes and the gate logic.

Use it

Prerequisites: a checkout of EvalArc at commit d13c9f7 with the evalarc command installed. examples/results-diff/inspect/baseline.json and current.json are bundled, scripted synthetic Inspect exports, so no input logs need to be created.

# Create a local stand-in for the GitHub step summary.
# In GitHub Actions, pass "$GITHUB_STEP_SUMMARY" instead.
: > step-summary.md
evalarc diff examples/results-diff/inspect/baseline.json examples/results-diff/inspect/current.json --output inspect-diff --markdown step-summary.md
echo "exit: $?"   # exit: 1 (the gate fails)
grep -A 12 '#### Why the gate failed' step-summary.md
grep -A 12 '#### Why the gate failed' inspect-diff/summary.md

Expected: the console lists three blocking checks: regressed refund-duplicate / includes, regressed refund-duplicate / match, and less_reliable cancel-pending / match. It also reports 1 within sampling noise. Both Markdown files contain 'Numeric scores pass at threshold 1; categorical verdicts use the source tool's pass mark.' and a table with those three rows. The Failing attempt cell for cancel-pending / match shows value I and evidence cancel:1006:queued. The section ends with a line rendered with code spans: Inputs: baseline `baseline.json` sha256 `<12 hex>`, current `current.json` sha256 `<12 hex>`. The prefixes depend on the bundled files. If you run the same command with baseline.json as both inputs, the gate passes and that summary has no such section.

Scope

Checks were executed by the controller, not by me; I only read its receipts. Base 0a9c96c: tests/test_feature_6401d7fe5951.py had 8 failures and 3 passes, as expected before the feature existed. Candidate d13c9f7: that test file, the full pytest suite, ruff check, ruff format --check, scripts/build_site.py and node scripts/check_site.cjs all exited 0. check_site.cjs is an existing showcase/browser regression check of the site pages at 1440, 390 and 320 px. It is not a visual review of this feature. The feature changes only Markdown text, and nobody has reviewed how GitHub renders it. Case and check share one column. Only evidence already in the exports is shown: graders are not rerun, missing samples are not rebuilt, and no reproduction commands are generated. The tests use the bundled synthetic Inspect example and synthetic edits of it. They pin rendering behavior only. They do not show that the explanations are accurate or useful on real runs, and they do not measure reviewer time or the EA-03 trial target. The provenance line is left out unless both runs record a source name and sha256. Tools that compare failing-gate summary.md files byte for byte will see the new section.

Upgrade and rollback

Upgrade by installing the release that contains commit d13c9f7. Existing commands, inputs, diff.json files, index.html reports, exit codes and gate outcomes stay the same. Passing-gate summaries do not change, and failing-gate summaries only gain the explanation section. If downstream tooling diffs or parses summary.md on failing gates, update it to allow the new '#### Why the gate failed' block. To roll back, pin the previous evalarc version. The section disappears, and no stored data or report folder needs migration.
