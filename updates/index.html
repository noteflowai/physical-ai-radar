noteflowai/dsh-skills-anywhere · 0.17.0 · 2026-10-01

record the Git source commit in MCP open_skill receipts

On candidate commit 59390b7, a successful MCP open_skill call that passes its expected_sha256 and expected_bundle_sha256 checks now returns structuredContent.receipt.source_commit. For a skill from a Git source, it is the 40-character lowercase HEAD SHA of that source's cache checkout at load time. For agent directories, plugin marketplaces and extra local directories it is null, and no Git command runs for them. For a Git source whose commit cannot be proven, it is also null and the server logs one 'skills-anywhere: source commit unavailable for <name>: <reason>' warning. That covers Git missing or failing, a timeout, or a work tree with no .git of its own or one outside the cache. The load still returns unchanged content in that case. Git runs without a shell and with GIT_* variables removed. Discovery stops at the cache directory, so the commit of an enclosing repository is never reported. Rejected loads throw their existing errors before any Git lookup. The advertised outputSchema declares source_commit. The schema string stays skills-anywhere-load-1. These are unchanged: loadReceipt(), LoadReceipt, OpenedSkill, the exported openSkill(), dsh provider and tool receipts, skill:// resources and rendered text. Controller-run checks on 59390b7: an acceptance-before run failed 3/3 feature tests because the receipt had only 11 fields. noteflowai/ai-chat-for-amazon-bedrock · 1.53.0 · 2026-09-30

count final Bedrock chat failures by cause on the dashboard

Version 1.53.0 makes failed Amazon Bedrock chat calls visible on the existing admin dashboard. The Usage today card has a fourth metric, Failed requests. The seven-day usage panel has one line, for example 'Failed chat requests, last 7 days: 4. Throttled 3, access denied 1.' When there are none it reads 'No failed chat requests recorded in the last 7 days.' The line also appears in the existing empty state. A site where every call fails no longer looks like a quiet site. A failure is counted once per handle_chat_message() or stream_chat_message() call, only if that call sent at least one Bedrock HTTP request and still returned an error after fallback and Converse adaptation retries. AI_Chat_Bedrock_Usage::classify_failure() sorts it into one of six categories using the HTTP status and the plugin error code: throttled (429), access_denied (401/403), validation (400), unavailable (5xx), network (status 0 with aicfab_unreachable or aicfab_stream_interrupted) or other. Some cases are not counted: - Missing credentials, an invalid region or model, the daily limit, and encoding errors. None of these send a request. - Retries that later succeeded. - Stopped streams. Only per-day category counts are stored in the existing ai_chat_bedrock_usage option. No message, prompt, output, error text, user ID or IP is kept. Requests, tokens, per-model counts and the daily cap still count successful invocations only. Controller-run checks on commit d1da36b: - Before the change, the new test failed with exit 255 (undefined classify_failure) on the base code. - tests/test_feature_364f48c382c4.php passed with assertions enabled. - bin/prerelease.sh passed: 47 suites including usage.php and admin-ux.php, phpcs clean, and versions all 1.53.0. - tests/tooling.php passed. - bin/build-package.py built the 1.53.0 zip. The stream_chat_message() return-path check that failed in the prior review now passes.

noteflowai/physical-ai-radar · 1.4.0 · 2026-09-30

claim-audit worksheet for recently published numeric claims (RA-01)

Adds python3 -m pairadar.claims, an offline, read-only command for the RA-01 claim review. It reads the published JSON Feed store (radar/feed.json by default). For each figure in the items[]._radar entries within the chosen window, it prints one row of a deterministic Markdown review sheet. The columns are #, day, evidence, claim, status, context, source and an empty review cell. Each status comes from distill.number_context applied to the stored text: - quoted: the figure was found in the stored excerpt. - title: the figure was found only in the title. - no-excerpt: the stored excerpt is empty, as it is for baseline entries. - unlocated: the figure is not in the stored title or truncated excerpt. Check the original source first. The reference day is the newest valid entry date, not the system clock. The header gives the store path, reference day, days, total figures T, rows shown S and skipped entries K. A whole-window status-count line always appears. When the sheet is capped, a line gives the number of hidden unlocated and no-excerpt figures and a --limit T rerun value. Items that are not objects, lack a _radar dict or have a non-canonical date are skipped and counted. Store problems (missing, unreadable or invalid JSON, wrong shape or version, no dated entries) exit 2 with one 'claims: ' stderr line and no traceback. noteflowai/evalarc · 0.16.1 · 2026-09-29

fix: fail the diff gate when a check has fewer assessed attempts than the baseline

evalarc diff now has a blocking change kind, less_covered. A check gets it when the current run assessed fewer attempts than the baseline and the pass rate did not fall. A smaller sample can no longer be reported as improved or unchanged. For example, 2/2 to 1/1, 1/2 to 1/1, and 2/2 to 1/1 with one unassessed attempt are all less_covered, and the command exits 1. The existing kinds still take precedence. A lower pass rate is still reported as regressed or less_reliable. A check that passed before and now has zero assessed attempts is still unassessed. The CLI now reads its list of blocking kinds from BLOCKING, so it prints lines such as ' less_covered: cancel-pending / match'. With --output, diff.json keeps schema evalarc.results-diff.v1 and lists less_covered in counts and changes. summary.md shows a 'less covered' row with the baseline and current fractions, and the index.html row uses the existing failed styling. Comparisons where no check lost assessed attempts give the same results as before. docs/ci-gate.md and docs/ci-gate.zh-CN.md list less_covered in the change table. noteflowai/physical-ai-radar · 1.3.0 · 2026-09-29

score keyword lane classification against a labeled shortlist

python3 -m pairadar.lanes has a new --labels PATH option. It compares the keyword lane classifier with a hand-labeled JSON file. For each entry it scores title + '. ' + summary using ranked_lanes, whose top lane is the one distill.classify picks. It then applies the existing thin/ambiguous rules. Those rules now live in a flag_reasons helper that inspect() also calls. The command prints a JSON report with: - labels: the file's basename only - labeled and margin - agreement for all, confident (unflagged) and flagged entries, each as n, agree and rate (rate is null when n is 0) - disagreements in input order, each with id (null when absent), title, label, predicted, reasons, best and runner_up A disagreement with reasons [] is a confident misfile that the flags missed. The whole file is validated before anything is scored. Invalid input exits 2 with one 'lanes: ' stderr line and empty stdout. This covers an unreadable file, invalid JSON or non-UTF-8 text, no items list, a non-object entry, an empty or non-string title or lane, a non-string id or summary, an unknown lane (the valid ids are listed), and combining --labels with --latest or --fail-on-suspicious. In labels mode the exit code is 0 whenever a report is printed. docs/METHODOLOGY.md section 9 documents the format and its limits. The controller ran the checks, not me. In the pre-feature run, 8 of the 10 feature tests errored because argparse rejected --labels. On candidate c109acf the controller ran python -m pairadar --rerender --no-readme (exit 0), the 10 feature tests (all passed) and the full unittest suite (446 tests, OK).

noteflowai/physical-ai-radar · 1.2.0 · 2026-09-27

report consecutive-failure streak and failing_since date for struggling sources in pairadar.health

`python3 -m pairadar.health` now tells the maintainer and the nightly repair gate whether a struggling source has been continuously dark or is flapping. Each entry under `struggling` gains two fields next to the existing `source` and `failed_days`: `streak_days`, the number of consecutive runs (counted back from the latest run that recorded health inside the window) on which the source appears in `failed`, and `failing_since`, the `date` of the oldest run in that streak. A run on which the source answered, was served by its fallback endpoint, or was not attempted ends the streak. A new public helper `health.streak(runs, reference, window, source)` returns `(streak_days, failing_since)` and `(0, None)` when the source did not fail the latest run. All previously emitted keys (`reference`, `window_days`, `threshold_days`, `runs_with_health`, `failures`, `fallbacks`, and `source`/`failed_days` inside `struggling`), the worst-first ranking, the threshold and latest-run rules, and `--fail-on-struggling` exit codes are unchanged. The module docstring and docs/automation.md explain the two fields.
