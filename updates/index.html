noteflowai/robot-reel · 0.19.0 · 2026-10-04

seal one frame/channel finding into a LeRobot replay bundle

Adds a --mark option to the existing robot-reel lerobot command: robot-reel lerobot EXPORT_DIR --mark FRAME --signal KEY/NAME [--signal ...] --note TEXT. It runs verify() on the export first. It then writes one finding.json containing: the episode, the zero-based frame, timestamps[frame], 1 to 8 key/name/value signals read from episode.json, the note, the manifest hash of episode.json, the package version (or null) and a fixed limitations statement. The sha256 of finding.json is added to manifest.json, and every other manifest entry stays the same. With --verify, alone or with --check-media / --check-source, the JSON result includes the sealed finding. An unmarked export gives the same result as before. Verify exits 2 with a named error if finding.json was edited without re-hashing, if finding.json is present but not listed in the manifest, if a listed finding.json is missing, if episode.json or a clip changed, or if a re-hashed finding disagrees with episode.json or breaks the input rules. Invalid --mark arguments, an already-marked export and any verify failure exit 2 and write nothing. If the manifest replacement fails, --mark removes the finding.json it placed in that run. noteflowai/ai-chat-for-amazon-bedrock · 1.53.0 · 2026-09-30

count final Bedrock chat failures by cause on the dashboard

Version 1.53.0 makes failed Amazon Bedrock chat calls visible on the existing admin dashboard. The Usage today card has a fourth metric, Failed requests. The seven-day usage panel has one line, for example 'Failed chat requests, last 7 days: 4. Throttled 3, access denied 1.' When there are none it reads 'No failed chat requests recorded in the last 7 days.' The line also appears in the existing empty state. A site where every call fails no longer looks like a quiet site. A failure is counted once per handle_chat_message() or stream_chat_message() call, only if that call sent at least one Bedrock HTTP request and still returned an error after fallback and Converse adaptation retries. AI_Chat_Bedrock_Usage::classify_failure() sorts it into one of six categories using the HTTP status and the plugin error code: throttled (429), access_denied (401/403), validation (400), unavailable (5xx), network (status 0 with aicfab_unreachable or aicfab_stream_interrupted) or other. Some cases are not counted: - Missing credentials, an invalid region or model, the daily limit, and encoding errors. None of these send a request. - Retries that later succeeded. - Stopped streams. Only per-day category counts are stored in the existing ai_chat_bedrock_usage option. No message, prompt, output, error text, user ID or IP is kept. Requests, tokens, per-model counts and the daily cap still count successful invocations only. Controller-run checks on commit d1da36b: - Before the change, the new test failed with exit 255 (undefined classify_failure) on the base code. - tests/test_feature_364f48c382c4.php passed with assertions enabled. - bin/prerelease.sh passed: 47 suites including usage.php and admin-ux.php, phpcs clean, and versions all 1.53.0. - tests/tooling.php passed. - bin/build-package.py built the 1.53.0 zip. claim-audit worksheet for recently published numeric claims (RA-01)

Adds python3 -m pairadar.claims, an offline, read-only command for the RA-01 claim review. It reads the published JSON Feed store (radar/feed.json by default). For each figure in the items[]._radar entries within the chosen window, it prints one row of a deterministic Markdown review sheet. The columns are #, day, evidence, claim, status, context, source and an empty review cell. When the sheet is capped, a line gives the number of hidden unlocated and no-excerpt figures and a --limit T rerun value. Items that are not objects, lack a _radar dict or have a non-canonical date are skipped and counted. Store problems (missing, unreadable or invalid JSON, wrong shape or version, no dated entries) exit 2 with one 'claims: ' stderr line and no traceback. noteflowai/physical-ai-radar · 1.2.0 · 2026-09-27

report consecutive-failure streak and failing_since date for struggling sources in pairadar.health

`python3 -m pairadar.health` now tells the maintainer and the nightly repair gate whether a struggling source has been continuously dark or is flapping. Each entry under `struggling` gains two fields next to the existing `source` and `failed_days`: `streak_days`, the number of consecutive runs (counted back from the latest run that recorded health inside the window) on which the source appears in `failed`, and `failing_since`, the `date` of the oldest run in that streak. A run on which the source answered, was served by its fallback endpoint, or was not attempted ends the streak. A new public helper `health.streak(runs, reference, window, source)` returns `(streak_days, failing_since)` and `(0, None)` when the source did not fail the latest run. All previously emitted keys (`reference`, `window_days`, `threshold_days`, `runs_with_health`, `failures`, `fallbacks`, and `source`/`failed_days` inside `struggling`), the worst-first ranking, the threshold and latest-run rules, and `--fail-on-struggling` exit codes are unchanged. The module docstring and docs/automation.md explain the two fields.
